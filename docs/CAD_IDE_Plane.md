# Vision & Architecture: Next-Gen cQED Open-Source IDE

## 1. Executive Summary
Цель проекта — создание открытой интегрированной среды разработки (IDE) для моделирования систем квантовой электродинамики цепей (cQED). Система переходит от монолитной архитектуры (Mathematica) к модульной мультиязычной платформе, объединяющей гибкость Python, математическую мощь Julia и производительность C++.

## 2. The Core Philosophy: "The Two-Language Problem" Solved
Проект строится на преодолении разрыва между исследовательской гибкостью и вычислительной мощностью.
* **Исследовательский слой:** Описание физики на языке математики.
* **Вычислительный слой:** Мгновенная компиляция формул в машинный код.

## 3. High-Level Architecture (The Triple-Stack)

Система разделена на три функциональных слоя:

| Слой | Технология | Роль в проекте |
| :--- | :--- | :--- |
| **Frontend & Orchestrator** | **Python (PySide6/Qt)** | Интерфейс пользователя, управление графом зависимостей (Registry), скриптинг для юзера. |
| **Mathematical Engine** | **Julia (Symbolics.jl)** | Символьный вывод (S-матрицы, BIC), JIT-компиляция численных свипов, решение дифференциальных уравнений. |
| **System Layer** | **C++ / Fortran** | Низкоуровневое управление памятью (Shared Memory), драйверы измерительного оборудования, геометрические операции. |

---

## 4. The Math Engine: Why Julia?

Julia выбрана как основной вычислительный узел по следующим причинам:

### 4.1. Symbolics.jl vs Mathematica
В отличие от классических систем, Julia рассматривает символьные выражения как объекты, которые можно скомпилировать. 
* **Аналитика:** Генерация уравнений для S-матриц и условий BIC.
* **Кодогенерация:** Функция `build_function` превращает аналитическую формулу в высокопроизводительный LLVM-код «на лету». Это заменяет JIT-конвейер Mathematica, обеспечивая ту же (или более высокую) скорость без проприетарных лицензий.

### 4.2. Multiple Dispatch
Позволяет писать универсальные алгоритмы (например, поиск корней или оптимизация потенциала), которые работают с любыми типами данных — от обычных `Float64` до сложных символьных деревьев и тензоров на GPU, сохраняя нативную скорость C++.

### 4.3. Differential Programming
Возможность автоматического дифференцирования всей цепочки расчета. Это критически важно для:
* Поиска минимумов многомерных потенциалов ($\phi_{min}$).
* Параметрической оптимизации квантовых схем.

## 5. The Orchestrator: Python as the System Manager

Python выступает в роли «клея» и главного диспетчера (Orchestrator), который не занимается тяжелыми вычислениями, но управляет всеми процессами в IDE.

### 5.1. Dependency Graph (Registry)
Вместо жестко прописанных путей используется динамический направленный ациклический граф (DAG).
* **Smart Invalidation:** Если пользователь меняет значение внешнего потока ($\Phi_{ext}$), менеджер помечает зависимые узлы (Phases, S-Matrix) как "stale" (устаревшие).
* **Lazy Evaluation:** Расчет инициируется только тогда, когда данные требуются для отображения на графике или экспорта, что экономит ресурсы процессора.

### 5.2. GUI & User Interaction (PySide6)
* **Node-Based Interface:** Визуальный конструктор схем, где каждый элемент (джозефсоновский переход, емкость) — это объект Python, транслируемый в математическую модель для Julia.
* **Asynchronous Execution:** Все вызовы к Julia-ядру выполняются в отдельных потоках, чтобы интерфейс оставался отзывчивым даже во время тяжелых свипов.

### 5.3. Scripting API
Поскольку менеджер написан на Python, IDE предоставляет пользователю нативный API. Любое действие в GUI генерирует Python-код, что позволяет легко автоматизировать эксперименты и интегрироваться с внешними библиотеками (NumPy, SciPy, ML-стек).

## 6. The Technical Layer: C++ Responsibilities

C++ используется точечно там, где Julia или Python не могут обеспечить нужный уровень контроля над системными ресурсами.

### 6.1. Zero-Copy Data Sharing (Apache Arrow)
Для передачи гигантских массивов данных (например, результатов многомерного свипа) между Julia и Python используется **Apache Arrow**. C++ слой управляет сегментами Shared Memory, позволяя обоим языкам "смотреть" на одни и те же данные в памяти без затрат на копирование и сериализацию.

### 6.2. Hardware Abstraction Layer (HAL)
* **Instrumentation:** Подключение к лабораторному оборудованию (VNA, AWG, Digitizers). Большинство драйверов поставляются в виде C-библиотек. C++ обеспечивает стабильную и быструю прослойку для управления железом в реальном времени.
* **Real-time Processing:** Первичная обработка сигналов с АЦП перед передачей их в математическое ядро.

---

## 7. Inter-Process Communication (IPC) & Scalability

IDE спроектирована как распределенная система:
* **gRPC / ZeroMQ:** Основной протокол общения между Python-интерфейсом и Julia-решателем. Это позволяет запускать расчетное ядро на удаленном сервере или кластере, сохраняя GUI на локальной машине.
* **Containerization:** Математическое ядро Julia упаковывается в Docker-контейнер или Conda-окружение, что решает проблему "Dependency Hell" и обеспечивает воспроизводимость результатов расчетов.

---

## 8. Open Source & Community Vision

Архитектура «Python + Julia» делает проект максимально доступным для контрибьюторов:
1. **Физики** могут добавлять новые модели и решатели на Julia, используя привычный математический синтаксис.
2. **Программисты** могут улучшать UI и логику управления на Python.
3. **Системные инженеры** могут оптимизировать низкоуровневые узлы на C++.

Этот подход создает экосистему, способную конкурировать с закрытыми коммерческими пакетами за счет прозрачности алгоритмов и коллективного интеллекта научного сообщества.
