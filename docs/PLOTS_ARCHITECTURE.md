# Архитектура Графиков (Plots Architecture)

Этот документ описывает принципы построения визуализаций в пакете QED, основанные на парадигме ленивых вычислений (Lazy Evaluation) и использовании JIT-конвейеров.

## 1. Базовые принципы проектирования (Core Principles)

Все функции визуализации (в модуле `Plots.wl`) проектируются как «чистые потребители» данных. При создании новых графиков необходимо соблюдать следующие архитектурные стандарты:

* **Делегирование состояния (State Delegation):** Функции графиков не управляют состоянием, инвалидацией кэша или триггерами перерисовки. Они не должны содержать механизмов хэширования или фиктивных аргументов. Управление состоянием полностью делегировано глобальному иммутабельному кэшу интерфейса (`Interactive.wl`).
* **Использование JIT-конвейеров (JIT Sweeps):** Любой график, сканирующий пространство параметров (поток, частота), обязан запрашивать данные через генератор пайплайнов: `QED`Numeric`GenerateSweepPipeline`. Это гарантирует, что все скрытые зависимости (например, пересчет матриц емкостей $C^{-1}$) резолвятся до начала цикла отрисовки.
* **Строгая типизация защищенных функций (Strict Typing):** Внутренние функции (например, целевая функция для `Plot`), передаваемые в механизмы рендеринга Mathematica, обязаны использовать проверку типов `_?NumericQ`. Это блокирует попытки FrontEnd-а выполнить предварительный символьный анализ конвейера, который может привести к ошибкам.
* **Статическое разрешение (Fixed Resolution):** Динамическое изменение качества рендеринга (например, использование встроенного `ControlActive`) не применяется. Высокая интерактивность при движении ползунков обеспечивается исключительно связкой JIT-движка и умного кэша, поэтому параметры качества фиксируются на оптимальных значениях (например, `PlotPoints -> 50`, `MaxRecursion -> 2`).

## 2. Графики рассеяния (S-Parameters)

Графики S-параметров демонстрируют работу одноступенчатого JIT-конвейера, где тяжелая математика (обращение матриц) вынесена за пределы цикла сканирования по частоте.

### 2.1. PlotFrequencyResponse
**Назначение:** Отображает спектр амплитуды S-параметров ($|S_{11}|$ или $|S_{21}|$) от частоты при фиксированном внешнем магнитном потоке ($\Phi_{ext}$).

**Архитектурная логика:**
1. Функция извлекает текущую рабочую точку $\Phi_{ext}$ из статических правил модели.
2. Запрашивается конвейер `GenerateSweepPipeline[model, "SMatrix"]`. На этом этапе математическое Ядро проверяет актуальность матриц $C^{-1}$ и $L_{eff}^{-1}$ и фиксирует их.
3. Конвейер возвращает чистую функцию `sMatrixAtPhi[f]`, вычисляющую S-матрицу с помощью разложения Шура.
4. Встроенная функция `Plot` сканирует только частоту, не вызывая пересчета физики схемы.

### 2.2. PlotSParameterMap
**Назначение:** Строит двумерную спектрограмму (DensityPlot) S-параметров в пространстве параметров "Внешний поток — Частота".

**Архитектурная логика:**
1. Конвейер `GenerateSweepPipeline[model, "SMatrix"]` возвращает генератор, принимающий внешний поток.
2. Двумерный сканпер `DensityPlot` адаптивно вызывает этот генератор на сетке потоков. Для каждого уникального $\Phi_{ext}$ конвейер пересчитывает эффективные индуктивности, а затем сканирует частотный диапазон.
3. Визуальная легенда (`BarLegend`) формируется как независимый семантический объект и прикрепляется через обертку `Legended`. Это изолирует графические директивы легенды от основного полотна тепловой карты.

## 3. Анатомия сложных графиков (на примере T1 и T_phi)

Функции построения времен когерентности (`PlotRelaxationTime`, `PlotDephasingTime`) имеют сложную внутреннюю структуру. В отличие от простых графиков, они отображают сразу несколько кривых (для разных мод) и требуют тяжелой матричной алгебры на каждом шаге интегрирования.

Логика работы таких функций строго разделена на 3 этапа для достижения максимальной производительности:

### 3.1. Этап 1: Статическая подготовка (Static Setup)
Любые вычисления, которые не зависят от внешнего магнитного потока, выполняются **строго один раз** до начала отрисовки графика.
* Из модели извлекаются узлы, переменные (потоки, заряды) и физические константы.
* Дифференцирование операторов (например, расчет градиентов операторов тока `currentGradient` и напряжения `voltageGradient`) происходит символьно один раз. Это избавляет систему от необходимости брать производные на каждом шаге цикла.

### 3.2. Этап 2: Генерация JIT-конвейера (Sweep Generation)
Для получения динамических данных график запрашивает у математического Ядра конвейер диагонализации:
`sweepFunc = QED`Numeric`GenerateSweepPipeline[model, "HarmonicDiagonalization"];`
Эта функция возвращает быстрое JIT-замыкание, которое при вызове `sweepFunc[phi]` мгновенно отдает свежие собственные частоты и матрицы трансформаций (`Nmat`, `Mmat`) для конкретной точки потока.

### 3.3. Этап 3: Динамическая алгебра и локальный кэш (Dynamic Execution & Cache)
Самая важная архитектурная особенность — это то, как график обрабатывает запросы от встроенной функции `Plot`. 

Функция `Plot` вычисляет значения **покриво** (per-curve). Если на графике 3 моды, для отрисовки точки $X = 0.25$ функция `Plot` сделает 3 независимых вызова: для 1-й, 2-й и 3-й моды. Если на каждый вызов запускать матричную диагонализацию, график будет строиться катастрофически долго.

Для обхода этой особенности внутри модуля графика реализуется паттерн **Локального кэша выполнения (Execution Cache)**:

1. Создается внутренняя функция `computeRates[phi]`, которая принимает поток, вызывает `sweepFunc[phi]`, рассчитывает матричные элементы $\langle 0 | \hat{O} | k \rangle$ и возвращает **сразу весь массив** значений (для всех мод).
2. Создается диспетчер `getRate[i, phi]`, который запоминает последнюю вычисленную точку:

```mathematica
lastPhi = "Init";
lastRates = {};

getRate[i_Integer, phi_?NumericQ] := (
   (* Если координата X изменилась — делаем тяжелый пересчет *)
   If[phi =!= lastPhi,
      lastPhi = phi;
      lastRates = computeRates[phi];
   ];
   (* Возвращаем заранее вычисленное значение для конкретной моды *)
   If[i <= Length[lastRates], lastRates[[i]], Null]
);
```
**Результат**: Матричная алгебра и вызовы JIT-движка выполняются строго 1 раз для каждой физической точки оси X. Значения Null используются для безопасного разрыва линий на графике (например, если частота моды падает до нуля или точка уходит в бесконечность).
